# TO-BE: целевая архитектура

## Выбор архитектурного стиля

Рассматривали три варианта.

**Оставить монолит и масштабировать его.** Можно добавить реплик и железа, но монолит масштабируется только целиком, а главное узкое место — одна база и синхронная цепочка — никуда не денется. До 18 000 RPS при 100 мс так, возможно, дотянуть получится, до 50 000 RPS и мультирегиона точно нет.

**Сразу переписать на микросервисы.** За три месяца командой из 35 человек без SRE это нереально. Big bang-миграция означает долгий период, когда новую систему уже пишут, а старую ещё надо поддерживать, и большой риск сорвать подключение DSP.

**Постепенная декомпозиция по Strangler Fig.** Новые сервисы ставим рядом с монолитом, перед ними API Gateway, и трафик переключается на сервис по мере его готовности. Монолит постепенно «усыхает». Модульный монолит используем как промежуточное состояние для тех частей, которые выносим не сразу: внутри монолита разделяем модули и запрещаем им лезть в чужие таблицы.

Выбираем третий вариант. Порядок выноса определяется тем, что сильнее всего мешает SLA: сначала сервис ставок и запись событий, потом остальное. Подробнее в [ADR-001](adr/ADR-001-evolution-strategy.md) и [ADR-002](adr/ADR-002-bidding-service-first.md).

## Этапы

### Этап 1, 0–3 месяца: промежуточное решение

Цель — подключить DSP: 18 000 RPS, P95 не выше 100 мс, сервис ставок не падает.

- Перед всеми входящими запросами DSP ставим API Gateway (Envoy): аутентификация партнёров, rate limiting, маршрутизация, метрики latency.
- Выносим из монолита сервис ставок (Auction Engine). Данные кампаний и бюджеты он берёт из Redis, а не из PostgreSQL. Сервис масштабируется горизонтально.
- Поднимаем Kafka. Показы и клики пишутся в топики, а не в базу. Статистика читает их из Kafka и пишет агрегатами пачками.
- Для аналитики поднимаем read replica PostgreSQL, тяжёлые запросы уходят с основной базы.
- Вынесенные сервисы сразу контейнеризируем, для них настраиваем CI/CD и мониторинг (Prometheus, Grafana, трассировка).
- Ad Server, Delivery, финансы и кабинет пока остаются в монолите.

### Этап 2, 3–12 месяцев: целевое решение

Цель — 50 000 RPS, SLA 99,9%, мультирегиональное развёртывание.

- Выносим остальные сервисы: подбор рекламы, выдачу, кампании, финансы, приём событий, статистику, аналитику.
- У каждого сервиса своя база (Database per Service).
- Статистика и аналитика переезжают в ClickHouse.
- Кабинет работает через BFF.
- Всё работает в Kubernetes в двух регионах. Горячий путь аукциона обслуживается в каждом регионе независимо.
- Монолит выключается.

## Сервисы и их границы

Границы проведены по бизнес-контекстам и по профилю нагрузки: горячий путь аукциона отделён от всего, что может подождать.

| Сервис | Ответственность | Почему отдельно |
|---|---|---|
| API Gateway (Envoy) | Вход для DSP: аутентификация, rate limiting, маршрутизация, circuit breaker | Единая точка контроля трафика партнёров и мониторинга SLA |
| Ad Selection | Определение пользователя, подбор кандидатов | Горячий путь, своя логика таргетинга, масштабируется вместе с трафиком |
| Bidding | Аукцион, расчёт ставки, проверка бюджета | Самый чувствительный к задержкам компонент, должен масштабироваться и деплоиться отдельно |
| Delivery | Формирование разметки ответа | Простой stateless-сервис, другой ритм изменений (шаблоны креативов) |
| Tracking | Приём событий показов и кликов | Огромный поток записи, не должен влиять на аукцион |
| Campaign | Кампании, креативы, таргетинг, ставки | Источник правды для настроек рекламодателя, транзакционные данные |
| Finance | Списания, балансы, счета | Строгие требования к целостности, отдельная ответственность |
| Statistics | Агрегация событий | Потоковая обработка, не связана с транзакциями |
| Analytics | Отчёты для рекламодателей | Тяжёлые аналитические запросы, отдельное хранилище |
| Dashboard BFF | API для кабинета | Собирает данные из нескольких сервисов под нужды интерфейса |

## Взаимодействие

- DSP → API Gateway: HTTPS, OpenRTB.
- Внутри горячего пути (Gateway → Ad Selection → Bidding → Delivery): gRPC. Он быстрее REST за счёт бинарного формата и постоянных соединений.
- События (показы, клики, результаты аукциона, списания): Kafka, асинхронно. Аукцион не ждёт, пока событие обработают.
- Изменения кампаний: Campaign публикует событие в Kafka и обновляет Redis, Bidding читает данные из Redis.
- Кабинет → BFF: REST. BFF → Campaign, Finance, Analytics: REST.

## Инфраструктурные компоненты

| Компонент | Назначение |
|---|---|
| Envoy | API Gateway для DSP |
| Kafka | Поток событий, развязка сервисов, подробнее в [ADR-003](adr/ADR-003-event-streaming.md) |
| Redis Cluster | Кеш кампаний и профилей, атомарные счётчики бюджетов |
| Kubernetes | Запуск и автомасштабирование сервисов |
| Prometheus, Grafana, Jaeger | Метрики, дашборды, трассировка запросов |

## Хранилища

| Сервис | Хранилище |
|---|---|
| Bidding, Ad Selection | Redis (данные кампаний, профили, бюджеты) |
| Campaign | PostgreSQL с репликами на чтение |
| Finance | PostgreSQL с синхронной репликой |
| Statistics, Analytics | ClickHouse |
| Tracking | Своего хранилища нет, пишет в Kafka |
