# Task1. Архитектурная диагностика и целевое видение AdScale

AdScale подключает крупную DSP-площадку. Нагрузка вырастет примерно до 18 000 RPS, а у партнёра жёсткие требования ко времени ответа. Текущий монолит уже сейчас работает на пределе: 15 000 RPS в пике и P95 110–120 мс при требовании 100 мс.

В этой папке:

- [AS-IS.md](AS-IS.md) — разбор текущей архитектуры: узкие места, точки отказа, влияние на время отклика;
- [drivers.md](drivers.md) — архитектурные драйверы: функциональные требования, атрибуты качества с приоритетами, ограничения;
- [TO-BE.md](TO-BE.md) — выбор стиля эволюции и целевая архитектура через год, план перехода;
- [diagrams/](diagrams/) — C4 Container целевой архитектуры (PlantUML);
- [adr/](adr/) — архитектурные решения:
  - [ADR-001](adr/ADR-001-evolution-strategy.md) — стратегия эволюции от монолита к микросервисам;
  - [ADR-002](adr/ADR-002-bidding-service-first.md) — сервис ставок выделяем первым;
  - [ADR-003](adr/ADR-003-event-streaming.md) — Kafka для потоковой обработки событий.

Коротко о решении: систему не переписываем, а постепенно выносим из монолита сервисы по паттерну Strangler Fig. Первым уходит сервис ставок, так как он стоит на критическом пути и определяет SLA. Одновременно запись событий переводится в Kafka, чтобы снять нагрузку с PostgreSQL. За три месяца это даёт запас для подключения DSP, а за год монолит полностью заменяется сервисами.
