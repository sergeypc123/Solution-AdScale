# Масштабирование баз данных

## Ориентиры по нагрузке через год

- 50 000 запросов на ставку в секунду, столько же записей результатов аукциона.
- Показов примерно в 3–5 раз меньше, чем запросов: около 10–15 тыс. событий в секунду.
- Кликов около 1% от показов: сотни событий в секунду.
- Изменений кампаний немного, это единицы в секунду.

## Репликация

| Хранилище | Схема | Зачем |
|---|---|---|
| Finance PostgreSQL | Master + синхронная реплика в другой зоне + асинхронная реплика во втором регионе | Без потери подтверждённых транзакций при отказе мастера. Асинхронная реплика нужна на случай отказа региона и для отчётов по финансам |
| Campaign PostgreSQL | Master + 2 асинхронные read replica | Чтение для кабинета и прогрева кеша не нагружает мастер. Небольшое отставание реплик допустимо |
| Redis Cluster | У каждого шарда master + 1 replica в другой зоне, автоматический failover | При падении узла реплика становится мастером за секунды |
| ClickHouse | ReplicatedMergeTree, 2 реплики на шард | Отказоустойчивость и распределение запросов на чтение |
| Kafka | Replication factor 3, min.insync.replicas = 2 | Потеря одного брокера не теряет данные |

## Шардирование

**Redis.** Redis Cluster сам раскладывает ключи по 16 384 слотам. Чтобы ключи одной кампании оказались на одном узле (это нужно для атомарного Lua-скрипта), используем hash tag: `campaign:{c123}`, `budget:{c123}:2026-10-26`. Счётчики частоты показов шардируются по пользователю: `freq:{u456}:c123`. При росте нагрузки добавляем узлы и перераспределяем слоты без остановки.

**ClickHouse.** Шардируем по `cityHash64(campaign_id)`, партиционируем по дню (`toYYYYMMDD(event_time)`). Отчёты почти всегда строятся по конкретной кампании и периоду, поэтому запрос попадает в один шард и в нужные партиции. Старые партиции удаляются целиком по TTL.

**Kafka.** Ключ партиции зависит от топика: для показов и кликов `campaign_id` (все события кампании идут по порядку в одну партицию, это нужно финансам), для результатов аукциона `request_id` (равномерное распределение).

**PostgreSQL (Campaign, Finance)** пока не шардируем. Объёмы небольшие, вертикального масштабирования и реплик хватит. Если понадобится, ключом шардирования будет `advertiser_id`: все операции рекламодателя останутся в одном шарде, транзакции не станут распределёнными.

## Read replicas для аналитики

На этапе 1 нужны. Пока аналитика в монолите, поднимаем read replica основной PostgreSQL и переводим на неё все аналитические запросы. Это быстро и сразу убирает тяжёлые запросы с мастера.

В целевом решении не нужны: аналитика переходит на ClickHouse, который сам распределяет чтение по репликам.

## CQRS

Применяем там, где нагрузка на чтение и запись очень разная:

| Где | Модель записи | Модель чтения |
|---|---|---|
| Кампании | PostgreSQL в Campaign Service | Redis для горячего пути аукциона, обновляется по событиям |
| Статистика и аналитика | Поток событий в Kafka | Агрегаты в ClickHouse (materialized views по часам и дням) |
| Финансы | Проводки в PostgreSQL | Балансы для кабинета читаются из реплики или проекции, обновляемой по событиям `balance-changes` |

Полноценный event sourcing не вводим: для команды это лишняя сложность, а нужного эффекта мы добиваемся и без него.
