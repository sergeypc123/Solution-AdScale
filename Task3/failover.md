# Отказоустойчивость данных

## RPO и RTO

RPO — сколько данных можем потерять, RTO — за сколько восстанавливаемся.

| Сервис / хранилище | RPO | RTO | Как достигаем |
|---|---|---|---|
| Finance (PostgreSQL) | 0 | 5 мин | Синхронная реплика в другой зоне, автоматическое переключение (Patroni). При отказе региона RPO до нескольких секунд из-за асинхронной реплики |
| Campaign (PostgreSQL) | ≤ 5 с | 10 мин | Асинхронные реплики, переключение через Patroni, PITR из WAL |
| Bidding (Redis) | ≤ 1 с | 1 мин | Реплика на каждый шард, AOF с fsync раз в секунду. Кампании восстанавливаются из Campaign и compacted-топиков, бюджеты — пересчётом в Finance |
| Statistics и Analytics (ClickHouse) | 0 по событиям | 1 ч | Реплики. Даже при полной потере данные можно перечитать из Kafka за 7 дней |
| Kafka | 0 | 5 мин | Replication factor 3, `acks=all`, зеркалирование во второй регион (MirrorMaker 2) |
| Ad Selection, Delivery, Tracking | нет состояния | 1 мин | Stateless, Kubernetes перезапускает экземпляры |

Самые жёсткие требования у финансов и у горячего пути аукциона. У аналитики требования мягче: отчёт на час позже рекламодатель переживёт, а сами события не теряются, потому что лежат в Kafka.

## Резервное копирование

| Хранилище | Что | Как часто | Где хранится |
|---|---|---|---|
| PostgreSQL (Finance, Campaign) | Полная копия + непрерывный архив WAL (pgBackRest), восстановление на любой момент времени | Полная раз в неделю, инкрементальная каждый день, WAL постоянно | Объектное хранилище в другом регионе, хранение 30 дней. Для финансов ещё ежемесячные копии на срок по требованиям закона |
| Redis | RDB-снимки | Раз в час | Объектное хранилище, 3 дня |
| ClickHouse | clickhouse-backup | Раз в сутки | Объектное хранилище, 14 дней |
| Kafka | Отдельно не бэкапим | | Защита за счёт репликации и зеркалирования во второй регион |
| Конфигурация, схемы, инфраструктура | Git | При каждом изменении | Git-репозиторий |

Восстановление проверяем раз в месяц: поднимаем копию из бэкапа в отдельном окружении. Бэкап, который ни разу не восстанавливали, считается непроверенным.

## Соответствие 12-факторным принципам

| Фактор | Как выполняем |
|---|---|
| 1. Одна кодовая база | Свой репозиторий у каждого сервиса, один и тот же код идёт во все окружения |
| 2. Зависимости | Явно описаны (go.mod, requirements.txt, conan), собираются в образ |
| 3. Конфигурация | Через переменные окружения и секреты Kubernetes. Адреса баз, ключи, лимиты в коде не хранятся |
| 4. Сторонние службы | PostgreSQL, Redis, Kafka, ClickHouse подключаются по адресу из конфигурации. Их можно заменить, например, на реплику при failover, без изменения кода |
| 5. Сборка, релиз, выполнение | CI собирает образ, релиз — это образ плюс конфигурация, запуск в Kubernetes. Никаких правок на сервере |
| 6. Процессы | Сервисы stateless, состояние только во внешних хранилищах. Поэтому падение экземпляра не теряет данные |
| 7. Привязка портов | Каждый сервис сам слушает свой порт (gRPC, HTTP) |
| 8. Параллелизм | Масштабирование добавлением экземпляров (HPA в Kubernetes) |
| 9. Утилизируемость | Быстрый старт с прогревом кеша до readiness, корректное завершение: дообработать запросы, закоммитить offset Kafka, сбросить буфер событий |
| 10. Паритет окружений | Одинаковые образы и одинаковые версии баз во всех окружениях |
| 11. Логи | Пишем в stdout в JSON, собираем централизованно |
| 12. Административные задачи | Миграции схем и прогрев кеша запускаются как отдельные Kubernetes Jobs из того же образа |
