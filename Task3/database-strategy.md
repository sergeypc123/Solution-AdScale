# Database per Service

## Правило

Каждый сервис владеет своими данными. Другие сервисы не ходят в его базу напрямую: получают данные через его API или через события в Kafka. Это позволяет менять схему и масштабировать хранилище одного сервиса, не задевая остальные. Сейчас всё лежит в одной PostgreSQL, и именно это главная проблема (см. Task1/AS-IS.md).

## Выбор хранилищ

| Сервис | Тип базы данных | Обоснование |
|---|---|---|
| Сервис ставок | Redis Cluster (in-memory key-value) | Горячий путь с бюджетом 20 мс: нужно чтение за доли миллисекунды и атомарные операции для резервирования бюджета (Lua-скрипты, INCRBY). Данные небольшие и помещаются в память. Источник правды для кампаний — Campaign Service, поэтому потеря Redis не означает потерю данных |
| Сервис кампаний | PostgreSQL | Связанные сущности (рекламодатель, кампания, креатив, таргетинг), нужны транзакции и ограничения целостности. Нагрузка невысокая: изменения делают люди через кабинет. Команда хорошо знает PostgreSQL |
| Сервис статистики | ClickHouse | Огромный поток вставок (десятки тысяч событий в секунду) и агрегации по времени. Колоночное хранение сжимает данные в разы и быстро считает суммы и счётчики. PostgreSQL на такой записи и стал узким местом |
| Сервис аналитики | ClickHouse (отдельная база в кластере) | Тяжёлые аналитические запросы по большим периодам — это ровно то, для чего ClickHouse сделан. Аналитика получает данные из Kafka в свои таблицы и не мешает ни статистике, ни транзакциям |
| Сервис финансов | PostgreSQL | Деньги: нужны ACID-транзакции, строгая согласованность, уникальные ограничения для идемпотентности, аудит. Объём данных умеренный |

Дополнительно:
- **Ad Selection**: Redis, профили и сегменты пользователей, подбор кандидатов в горячем пути.
- **Tracking**: своего хранилища нет, сервис только принимает события и пишет в Kafka.

## Как данные расходятся между сервисами

- Изменения кампаний: Campaign пишет в свою базу, публикует `campaign-changes` и обновляет Redis.
- Лимиты бюджетов: Finance задаёт дневной лимит в Redis, Bidding его расходует, Finance сверяет по событиям.
- Справочники для отчётов (названия кампаний и т. п.): Analytics берёт их из `campaign-changes` и хранит у себя копию.

## Миграция с общей базы

1. Внутри монолита у каждого модуля фиксируем список «своих» таблиц и запрещаем чтение чужих напрямую.
2. Запись событий переводим в Kafka, таблицы событий в PostgreSQL перестают расти.
3. Для каждого выносимого сервиса поднимаем отдельную базу, переносим данные, на время перехода синхронизируем через CDC (Debezium читает изменения из PostgreSQL и пишет в Kafka).
4. Переключаем запись на новый сервис, старые таблицы переводим в режим только для чтения, потом удаляем.
