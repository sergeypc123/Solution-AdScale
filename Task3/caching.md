# Кеширование

## Что кешируем

| Данные | Где | Как обновляем | TTL |
|---|---|---|---|
| Активные кампании, ставки, таргетинг | Redis + локальный снимок в памяти Bidding | Campaign пишет в Redis при изменении (write-through) и публикует событие | Redis: 10 мин как страховка, основное обновление по событию. Локальный снимок: 30 с |
| Бюджеты (остаток на день) | Redis | Это не кеш, а рабочие счётчики: Bidding уменьшает, Finance задаёт лимит и сверяет | Ключ на день, удаляется через 48 ч |
| Профили и сегменты пользователей | Redis (Ad Selection) | Обновляются по событиям показов и кликов | 24 ч |
| Frequency cap | Redis | Bidding увеличивает при показе | Равен окну ограничения |
| Шаблоны разметки креативов | Локальный кеш в Delivery | По событию изменения креатива | 5 мин |
| Отчёты в кабинете | Redis (BFF) | Кеш-aside: при промахе считаем и кладём | 1–5 мин в зависимости от периода отчёта |

Ставки не кешируем как готовый результат: каждый аукцион уникален. Кешируем входные данные для их расчёта.

## Где размещаем Redis

- Отдельный Redis Cluster для горячего пути (Bidding и Ad Selection) в каждом регионе, в тех же зонах доступности, что и сервисы. Задержка сети меньше 1 мс.
- Отдельный небольшой Redis для BFF и прочих некритичных кешей. Тяжёлый отчёт не должен вытеснять данные аукциона.
- Политика вытеснения для кластера горячего пути: `noeviction`. Данные бюджетов нельзя молча выкидывать, поэтому память мониторим и заранее расширяем. Для кеша BFF: `allkeys-lru`.

## Инвалидация

1. Campaign Service при изменении кампании обновляет Redis и публикует событие в `campaign-changes`.
2. Экземпляры Bidding читают этот топик и обновляют локальный снимок.
3. TTL работает как страховка, если событие потерялось.
4. При остановке кампании (например, закончились деньги) Finance публикует событие, и кампания убирается из Redis сразу. Это важно, чтобы не тратить чужие деньги.

Против одновременного истечения многих ключей (cache stampede) добавляем к TTL случайный разброс ±10%. При промахе только один запрос идёт за данными (single flight), остальные ждут его результат.

## Прогрев кеша

- **Новый экземпляр Bidding** перед тем, как начать принимать трафик, загружает все активные кампании из Redis в локальный снимок. Readiness probe не пропускает экземпляр в балансировку, пока загрузка не закончится.
- **Холодный старт Redis** (новый кластер, новый регион, восстановление после аварии): отдельная задача читает активные кампании и лимиты бюджетов из read replica Campaign и Finance и заливает их в Redis. Трафик на регион включается после её завершения.
- **Перед пиковыми часами** прогрев не нужен: активные данные и так держатся в памяти.

## Метрики

Hit ratio, latency Redis (P99), использование памяти, количество вытеснений. Алерт, если hit ratio горячего пути ниже 99% или память выше 75%.
