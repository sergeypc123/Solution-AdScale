# Взаимодействие и протоколы

## Общая схема

DSP → API Gateway (Envoy) → Ad Selection → Bidding → Delivery → ответ DSP.
Параллельно Bidding пишет результат в Kafka, а пользовательские показы и клики приходят в Tracking и тоже уходят в Kafka. Statistics, Finance и Analytics читают события из Kafka.

Диаграммы: [sequence](diagrams/bid-request-sequence.puml), [компоненты](diagrams/bidding-components.puml).

## Выбор протоколов

| Взаимодействие | Протокол | Почему |
|---|---|---|
| DSP → AdScale | HTTPS, OpenRTB 2.5/2.6, JSON | Отраслевой стандарт, его требует партнёр. Свой формат DSP поддерживать не будет |
| Gateway → Ad Selection → Bidding → Delivery | gRPC (HTTP/2, Protobuf) | Горячий путь, важна каждая миллисекунда |
| Bidding, Tracking → Statistics, Finance, Analytics | Kafka | Поток событий, несколько потребителей, ответ не нужен |
| Campaign → Bidding | Kafka (campaign-changes) + Redis | Bidding не должен синхронно ходить в Campaign |
| Кабинет → BFF → Campaign, Finance, Analytics | REST/JSON | Нагрузка небольшая, важнее простота и удобство отладки |

### Почему gRPC, а не REST, для Bidding

- Бинарный Protobuf сериализуется в несколько раз быстрее JSON и занимает меньше места.
- HTTP/2 держит постоянные соединения и мультиплексирует запросы, не тратит время на установку соединения.
- Строгий контракт в .proto: ошибки несовместимости видны на этапе сборки, а не в проде.
- Дедлайны встроены в протокол: клиент передаёт, сколько времени осталось, и сервис может не начинать работу, которую всё равно не успеет закончить.

REST здесь был бы проще для отладки, но на 18–50 тыс. RPS с бюджетом в десятки миллисекунд накладные расходы JSON и HTTP/1.1 заметны.

### Почему Campaign не вызывается синхронно

Данные кампаний читаются на каждый запрос, а меняются редко. Если Bidding будет каждый раз ходить в Campaign Service, тот станет таким же узким местом, каким сейчас является база. Поэтому Campaign при изменении пишет данные в Redis и публикует событие, а Bidding читает только Redis. Задержка обновления в несколько секунд для бизнеса приемлема.

### Почему Kafka для событий

- Событий много (показы, клики, результаты аукциона), и они нужны сразу нескольким сервисам.
- Аукциону не нужно ждать, пока событие обработают, поэтому синхронный вызов здесь только добавляет latency и риск.
- Kafka хранит события несколько дней. Если статистика или финансы упали, они перечитают события и ничего не потеряют.
- Масштабируется партициями до любых наших объёмов.

### Нужен ли API Gateway

Нужен, но только для внешнего трафика от DSP. В нём собраны аутентификация партнёров, rate limiting, маршрутизация между монолитом и новыми сервисами на время миграции (Strangler Fig), а также единые метрики latency для контроля SLA. Выбор и настройка описаны в [api-gateway.md](api-gateway.md).

Внутри между сервисами gateway не ставим, потому что каждый лишний hop добавляет задержку. Service mesh пока тоже не вводим: команде без SRE это лишняя сложность на первом этапе. Вернёмся к нему, когда сервисов станет больше десяти.

## Бюджет времени ответа

Требование DSP — 80 мс. Внутренний таймаут ставим меньше, чтобы гарантированно успеть ответить хотя бы no-bid.

| Шаг | Бюджет, мс |
|---|---|
| Envoy: TLS, аутентификация, rate limit, маршрутизация | 5 |
| Ad Selection: пользователь и кандидаты (Redis) | 15 |
| Bidding: правила, ставка, резерв бюджета (Redis) | 20 |
| Delivery: разметка | 5 |
| Сеть и сериализация между сервисами | 10 |
| Запас | 15 |
| **Таймаут на Gateway** | **70** |

Каждый сервис получает оставшееся время через gRPC deadline. Если до дедлайна не успевает, сразу возвращает no-bid.
